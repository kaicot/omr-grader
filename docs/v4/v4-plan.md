- 상태: 4.0.0으로 배포(빌드 25, GitHub 릴리즈 `v4.0.0`). 결과와 계획과 다른 점은 8절,
  릴리즈 기록은 [4.0.0](../releases/4.0.0.md). 화면·속도·결과 Excel을 고친
  [4.0.1](../releases/4.0.1.md)(빌드 26, GitHub 릴리즈 `v4.0.1`)은 판독 엔진을 바꾸지 않았고, 양식 자동 인식은
  앞 6장으로 정한다(실제 시험으로 다시 검증). [4.0.2](../releases/4.0.2.md)(빌드 27, `v4.0.2`)는
  결과 Excel 구성과 페이지 이미지 저장 형식(JPEG)을 바꿨다. [4.0.3](../releases/4.0.3.md)
  (빌드 28, `v4.0.3`)은 결과 Excel 탭·파일명, 인식 후 안내, 대시보드를 고쳤다.
  [4.0.4](../releases/4.0.4.md)(빌드 30, `v4.0.4`)는 휴지통과 대시보드 갱신 오류를 고쳤다.
  [4.1.0](../releases/4.1.0.md)(빌드 32, `v4.1.0`)는 문항 분석·판독 근거 탭과 합산 성적표를 더했다.
- 기준 코드: `fix/live-grading-20261006` 브랜치의 2.1.3 (`b6a0b06`), 작업 브랜치 `feat/v4`
- 제품 버전: 4.1.0

## 1. 배경

같은 실제 시험 스캔 24장(2개 파트 × 12장, 100문항, 학번 8자리)을 세 엔진으로 비교했다.

| 엔진 | 칸 위치 기준 | 결과 |
|---|---|---|
| v1 (단일 파일) | 답안표 바깥 테두리 네 모서리 + 고정 좌표 | 학번 24/24, 작은 점 표기는 빈칸 처리 |
| v2 (v1 + GUI, 감도 6) | v1과 같음 + 조명 보정 | 학번 24/24, 잡음으로 '중복' 오판 4건 |
| v3 2.1.0 | 종이 가장자리 + 손으로 그린 템플릿 | 5장 칸 어긋남, 3장 뒤집힘, 틀린 답 65개를 '정상'으로 표시 |
| v3 2.1.3 | 같음 + 정렬 재시도 | 답은 v1·v2와 일치, 학번이 자주 실패 |

v3가 약한 원인은 측정으로 확인했다.

1. **기준점:** 종이 가장자리를 기준으로 하고 회전을 보정하지 않는다. 스캔은 0.16~0.66° 기울어 있어 답 칸이 평균 0.5~1.1mm, 학번 칸이 0.9~2.2mm 어긋났다. 학번 칸은 모든 장에서 위로 밀렸다.
2. **측정 창:** 칸 간격의 60% 크기 사각형을 재서 같은 마킹의 점수가 원 안쪽 측정의 절반이 된다. 빈칸 점수도 높아 가장 약한 실제 마킹과 빈칸이 구분되지 않는다.
3. **템플릿:** 손으로 그린 상자라 최선으로 맞춰도 평균 0.3mm, 최대 0.7mm 어긋난다. 템플릿 생성 도구는 어디에도 없다.

## 2. 목표와 범위

최우선 목표는 **객관식 채점의 정확도와 신뢰도**다. 틀린 답을 정상으로 내보내지 않는 것이 첫째이고, 사람이 봐도 분명한 표기는 검토 없이 읽는 것이 둘째다.

포함:

1. 템플릿 선택 없는 양식 자동 인식과 양식 기억
2. 장마다 인쇄된 동그라미 격자에 맞춘 정렬
3. 버블 안쪽 원 측정과 판정 기준 재조정
4. 학번 판독 강화와 명단 대조
5. 정답 파란 원, 오답 빨간 원, 확인 필요 주황 원만 그리는 채점 이미지
6. 실제 시험 24장 기준 자료와 자동 회귀 검사

제외 (다음 버전):

- 주관식 단답형 점수 입력. 양식 기억 형식에 '서술 영역' 종류를 예약해 두어 나중에 추가할 수 있게 한다.
- 손글씨 인식, 100문항 초과 양식, 9자리 이상 학번

화면 구성, 세션 저장, 채점, Excel 내보내기, 백업·복구는 v3를 유지한다.

## 3. 인식 엔진 설계

### 3.1 입력

- PDF는 원본 스캔 해상도 이상(기본 216 DPI)으로 렌더링한다. 판독용 이미지를 원본보다 작게 줄이지 않는다.
- 이미지 파일은 그대로 쓰고, 150 DPI 미만으로 추정되면 경고한다.

### 3.2 양식 인식 (템플릿 대체)

시험용 코드(기준 자료 폴더의 `scripts/prototype/autolayout.py`)로 실제 24장 모두에서 구조를 정확히 찾았다. 칸 중심은 인쇄된 동그라미 중심과 중앙값 0.19pt 차이였다.

1. 적응 이진화 후 윤곽선에서 원 후보를 찾는다(원형도, 채움 비율, 크기).
2. 가장 흔한 반지름을 버블 크기로 정하고 중복 후보를 합친다.
3. 이웃 후보의 방향으로 기울기를 구하고 바로 세운 좌표에서 열과 행을 묶는다.
4. 간격이 일정한 열 묶음마다 행 격자를 만든다. 빠진 행은 2칸까지 메우고, 양 끝의 원이 적은 행(손글씨, 머리말)은 잘라낸다.
5. 블록마다 (열, 행) → 이미지 좌표 아핀 변환을 맞춘다.
6. 블록 종류를 정한다. 세로 10칸은 학번, 가로 4~5칸은 문항이다. 5×10처럼 모양만으로 모호하면 인쇄된 숫자가 열 방향(문항)으로 같은지 행 방향(학번)으로 같은지 비교한다.
7. 문항 번호는 왼쪽 블록부터 위에서 아래로 매긴다.

양식 기억:

- 처음 보는 양식은 "학번 8자리, 객관식 50문항"처럼 요약과 미리보기를 한 번 보여 주고, 확인되면 포터블 루트 아래에 저장한다.
- 다음부터는 구조 서명(블록 수·크기·상대 위치)으로 자동 선택한다.
- 한 묶음 안에 다른 양식의 장이 섞이면 그 장만 검토로 보낸다.
- 정답표 문항 수와 인식 문항 수가 다르면 경고한다.
- 빈 양식 PDF가 있으면 PDF 글자층의 ①~⑤·⓪~⑨ 위치와 인쇄된 문항 번호로 정확하게 등록할 수 있다(선택 기능).
- 기존 `.omrtemplate`는 더 이상 필요 없다.

### 3.3 방향

종이 테두리나 잉크 밀도 점수 대신 양식 인식 결과로 판정한다. 0°에서 유효한 구조가 나오지 않으면 180°, 90°, 270°를 시도한다. 0°와 180°는 기억된 양식과의 일치도(학번 블록 위치, 숫자 순서)로 가린다.

### 3.4 장별 정렬

각 장에서 원 후보를 찾고, 기억된 양식의 버블 좌표와 대응시켜 전체 투영 변환(RANSAC)을 구한 뒤 블록별 아핀으로 다듬는다. 대응 비율이나 잔차가 기준에 못 미치면 추측하지 않고 그 장을 검토로 보낸다.

### 3.5 마킹 측정과 판정

- 버블 중심에서 반지름의 0.75배 원 안쪽만 잰다.
- 어두움 기준은 주변 종이 밝기에 대한 상대값으로 정한다.
- 판정은 단일 표기, 빈칸, 중복, 애매(검토) 넷이다.
- 기준값은 맞추는 자료와 확인하는 자료를 나눠서 정한다. 파트1의 표기·빈칸 분포로 기준값을 정해 파트2로 확인하고, 반대로도 한다. 두 방향 결과를 모두 보고하고, 두 방향 모두 통과하는 값만 쓴다. 감도 설정은 이 기준값에 대응시킨다.
- 수정테이프나 지운 자국이 있는 칸은 빈칸 쪽으로 판정되는지 확인한다.

### 3.6 학번

답과 같은 측정을 쓴다. 명단이 있으면 명단에 없는 학번이나 중복 학번을 검토로 보낸다.

### 3.7 채점 이미지

깨끗한 스캔 위에 다음만 그린다.

- 굵은 파란 원: 맞힌 답
- 굵은 빨간 원과 가는 파란 원: 틀린 답과 정답 위치
- 주황 원: 미응답·중복·확인 필요
- 문항 번호 칸의 빨간 ×, 상단의 점수와 범례

v3의 칸 상자·번호 표시는 진단용 옵션으로만 남긴다.

## 4. 데이터 모델

- 문항 슬롯은 v3와 같이 Q1~Q100으로 유지한다. 양식에 없는 문항과 정답표에 없는 문항은 UNASKED로 둔다.
- 학번은 최대 8자리다. 짧은 학번은 v3의 뒤쪽 빈 자리 처리 규칙을 따른다.
- 세션에는 그 시험에 쓴 양식 기억을 고정 사본으로 저장해 재채점이 재현되게 한다.
- 기존 v3 세션은 계속 열리고 조회되어야 한다.
- 문서(`AGENTS.md`, README, 릴리즈 노트)는 `resolve_portable_root()`와 `ManagedPaths` 계약에 맞춰 갱신한다.

## 5. 기준 자료와 합격 기준

기준 자료는 실제 학생 자료이므로 **저장소에 넣지 않는다.** 위치는 환경 변수 `OMR_V4_BASELINE_DIR`로 지정한다. 자료가 없으면 관련 테스트는 건너뛴다.

정답 데이터 구성:

1. v1·v2·v3(2.1.3) 판독의 다수결로 문항별 답과 학번을 정한다.
2. 엔진끼리 갈린 칸은 사람이 이미지를 보고 확정한다. 확인한 칸과 근거는 `review_log.md`에 남기고, 사용자가 종이 원본으로 일부를 대조할 수 있게 한다.
3. 결과(장별 학번, 문항별 답)를 JSON으로 저장한다.

주의: v3 2.1.3의 작은 점 규칙은 이 24장을 보며 맞춘 것이라 세 엔진의 다수결이 완전히 독립적이지는 않다. 정답 데이터의 신뢰는 사람이 확인한 칸에 크게 기댄다.

| 게이트 | 기준 |
|---|---|
| G1 기준 24장 | 파트1로 맞추고 파트2로 확인, 그리고 반대로 해서 두 방향 모두 학번 12/12, 답 1,200/1,200 일치, 틀린 답 0. 검토 표시는 사람이 봐도 애매한 칸에만 |
| G2 변형 내성 | 기준 장을 ±1.5° 회전, ±3% 확대·축소, ±10mm 이동, JPEG 품질 60, 밝기 ±20%로 바꿨을 때 확정 답이 다른 확정 답으로 바뀌지 않고 틀린 답이 새로 생기지 않음. 경계 칸이 검토로 바뀌는 것은 변형 한 종류당 장마다 2칸까지 허용 |
| G3 변형 양식 | 실제 장으로 만든 50문항+주관식 양식에서 1~50번 인식과 판독 일치 |
| G4 예전 스캔 | 개발 중에 보지 않는 예전 시험 스캔에서 v1·v2가 일치한 칸은 모두 일치 |
| G5 기존 검증 | 전체 테스트(알려진 환경 실패 제외), ruff, mypy, `verify-portable-folder.ps1 -Smoke Both -StrictShutdown` |
| G6 속도 | 장당 1초 이내 |

## 6. 작업 단계와 역할

| 단계 | 내용 | 담당 |
|---|---|---|
| P0 | 기준 자료 JSON, 회귀 검사 스크립트와 테스트 | 메인 세션 (Opus 5.5, medium) |
| P1 | 영향 범위 조사: 프로필 가져오기·선택 흐름, 파이프라인 진입점, 페이지 모델 생성, 오버레이, 스캔 화면, 설정, 관련 테스트 | `omr-explorer` 2~3개 병렬 (Haiku) |
| P2 | 엔진 핵심: 양식 인식, 장별 정렬, 측정, 판정, G1~G3 반복 | 메인 세션 (high) → 어드바이저 1회 |
| P3 | 통합: 스캔 실행과 양식 기억 연결, 템플릿 선택 제거와 확인 화면, 채점 이미지, 버전 4.0.0과 문서 | `omr-implementer` 순서대로 (Sonnet), 메인이 변경 검토 |
| P4 | 전체 테스트, 정적 검사, 기준 회귀, 빌드, 포터블 검증 | 백그라운드 명령. 실패할 때만 메인이 분석 |
| P5 | 변경 전체 독립 검토 → 어드바이저 최종 1회 → 빌드 보고 | `omr-reviewer` (Opus, high) |

규칙:

- 하위 에이전트 모델은 호출할 때마다 명시한다.
- 같은 파일을 여러 에이전트가 동시에 고치지 않는다.
- 커밋은 메인 세션만 한다. main 병합과 push는 별도 승인을 받는다.

## 7. 학생 자료 보호

- 원본 스캔, 명단, 정답표, 결과 폴더는 읽기만 한다.
- 학생 자료는 Anthropic 밖 서비스(Codex 등)로 보내지 않는다.
- 출력에는 이름을 쓰지 않는다. 학번은 앞 4자리만 보이고 나머지는 가린다.
- 학생 자료가 든 임시 파일은 `%TEMP%\omr-v4-*`에만 만들고 쓰고 나면 지운다.
- 기준 자료, 덤프, 이미지는 저장소에 커밋하지 않는다.

## 8. 구현 결과와 계획과 다른 점

게이트 결과는 [4.0.0 릴리즈 문서](../releases/4.0.0.md)에 있다. G1~G4는 통과했다. G6은 판독만
장당 약 1.05초로 목표(1초)에 조금 못 미친다.

계획과 달라진 점:

- **측정(3.5).** '버블 안쪽 어두운 면적' 대신 '주변 종이 대비 잉크 농도에서 같은 열의
  칠하지 않은 칸 수준을 뺀 값'으로 판정한다. 예전 스캔(G4)에서 진하게 인쇄된 숫자 때문에
  빈칸이 0.28까지 올라가 옅은 연필 표시와 구별되지 않았기 때문이다. 측정 원은 장마다
  인쇄된 원의 반지름을 재서 그 0.75배로 정한다.
- **기준값 독립성(3.5, 5).** 기준값 0.11/0.24는 두 파트를 교차로 확인했지만 최종 값은 두
  파트와 예전 스캔을 모두 본 뒤 정했다. G4 예전 스캔은 위 측정 변경의 원인 분석에 한 번
  썼으므로 완전한 미사용 자료가 아니다.
- **정렬(3.4).** 블록별 아핀 보정 없이, 같은 모양의 블록 하나로 시작해 모든 원의 상호 최근접
  쌍으로 투영 변환(RANSAC)을 4번 다듬는다. G1·G2에서 칸 어긋남이 없었다.
- **방향(3.3).** 0°와 180°는 학번 블록 위치 대신 '인쇄된 ①이 ⑤보다 옅다'와 문항 번호 위치로
  가린다. 표 모양 양식에서는 숫자 위치 단서가 약해 프로필이 거꾸로 만들어진 일이 있었다.
  장이 거꾸로 읽히면 그 장의 답과 학번을 모두 '확인 필요'로 돌리는 안전장치를 더했다.
  숫자 단서는 블록별 차이의 중앙값이 1.5 회색 단계 이상일 때만 쓴다(실제 양식 3.6~11.8,
  숫자 없는 동그라미 0.1 미만). 그렇지 않으면 문항 번호가 정한다. 숫자 없는 합성 양식에서
  잡음이 문항 번호 단서를 뒤집던 문제를 테스트 작성 중에 찾았다. ①이나 ⑤가 칠해진 줄은
  비교하지 않으므로, ①만 칠한 학생의 장도 뒤집혀 읽히지 않는다(독립 검토에서 80%가 ①이면
  뒤집히던 문제를 찾았다). 방향은 블록 전체로 정하고, 그다음에 머리글 줄을 뺀다.
- **양식 만들기(3.2).** 여러 장을 평균한 격자는 첫 장의 좌표에 있으므로, 표본들의 기울기
  중앙값이 아니라 평균 격자 자체의 행·열 방향으로 바로 세운다. 기울기가 서로 다른 장으로
  만든 양식에서 칸이 인쇄된 원에서 최대 2.7px 벗어나던 문제를 테스트 작성 중에 찾았다.
  평균의 기준은 첫 장이 아니라 다른 장들과 가장 잘 맞는 장이고, 그 장과 중앙값 오차가
  반지름의 절반을 넘는 장(뒤집혀 읽힌 장)은 평균에서 뺀다.
- **머리글 줄(3.2).** 문항 블록 위에 ①~⑤ 동그라미 줄을 인쇄한 양식은 그 줄이 1번으로
  잡혀 모든 번호가 한 칸씩 밀렸다(독립 검토). 블록의 안쪽 줄 90% 이상에 문항 번호가 있고
  첫 줄이나 끝 줄의 번호 자리 잉크가 안쪽 줄 중앙값의 15%와 0.015보다 모두 작을 때만 그
  줄을 뺀다. 실제 양식의 가장 옅은 첫 줄(1번)은 중앙값의 0.43, 합성 양식의 가는 "1"은 0.30이었다.
  번호가 인쇄되지 않은 양식은 이 방법으로 줄을 빼지 않는다. 번호 칸에 'No.' 같은 글자나 표
  선이 있는 머리글은 한 장으로는 알 수 없어서(재검토), 같은 구조의 표본이 3장 이상이면 어느
  장에서도 칠해지지 않은 블록 첫 줄을 머리글로 보고 뺀다. 조건은 첫 줄이 0장에서 칠해지고,
  둘째 줄이 3분의 2 이상에서 칠해지고, 블록 안쪽 줄의 절반 이상이 칠해진 것이다. 끝 줄은
  보지 않는다(시험이 블록 끝 문항을 안 쓸 수 있다). 모든 학생이 비운 실제 1번도 머리글로
  보일 수 있지만, 양식의 성질인 머리글 줄은 그 양식으로 보는 모든 시험에 영향을 주므로 이
  거래를 택했고, 뺀 줄 수를 확인 창에 알린다. 기준 회귀 도구(`learn_profile`)도 같은 함수를
  거치므로 G1~G3이 실제 양식에서 진짜 문항이 빠지지 않음을 확인한다. 재검토에서 이 판단이
  저장된 올바른 양식을 밀어낼 수 있음을 찾아, 인쇄된 그대로의 구조에 맞는 저장된 양식을 먼저
  찾고 줄 빼기는 새 양식에만 쓴다. 또 판독 때 문항 블록 바로 위·아래의 인쇄된 동그라미 줄에
  칠한 표시가 있으면 그 장을 믿지 않는다. 머리글 줄은 아무도 칠하지 않으므로 맞는 양식은
  막지 않고, 실제 문항 줄을 뺀 양식은 그 줄을 칠한 장마다 드러난다. 줄의 대부분이 진한 줄은
  인쇄된 머리글로 보고 표시로 세지 않는다. 저장된 양식을 다시 쓸 때 이번 묶음에서 아무도
  칠하지 않은 블록 첫 줄이 있으면 상태 줄에 알린다(1~2장으로 잘못 확정한 양식을 찾도록).
- **쌓인 블록 사이 빈 줄(3.2).** 격자를 이을 때 빠진 줄을 2줄까지 메우던 처리 때문에, 위아래로
  쌓인 블록 사이에 빈 줄이 한두 개 있으면 그 자리가 문항으로 세져 번호가 밀렸다(최종 검토).
  이제 동그라미가 하나도 없고 문항 번호도 인쇄되지 않은 안쪽 줄에서 블록을 나눈다. 수정
  테이프로 덮인 줄처럼 번호가 인쇄된 줄은 계속 메운다.
- **모든 답안지에서 빈 문항 경고.** 최종 검토가 제안한 채점 전 경고(정답표의 문항이 모든
  답안지에서 비어 있음)는 화면 전달 경로가 없어 다음 버전으로 미뤘다.
- **섞인 양식(3.2).** 양식에 없는 동그라미가 양식 동그라미 수의 20%를 넘는 장은 검토로
  보낸다. 작은 양식이 큰 양식의 장에 모두 맞아 나머지 문항이 조용히 '출제 안 함'이 되는
  것을 막는다. 기준 자료에서 맞는 양식은 1%(100문항)와 2.7%(50문항) 이하, 50문항 양식으로
  읽은 100문항 장은 68~77%였다. 양식 재사용 확인과 미리보기는 감지된 양식과 구조가 같은
  장만 쓴다.
- **안전장치.** 채점은 '확인 필요'인 답만 막고 장의 검토 상태는 보지 않는다. 그래서 정렬이
  약한 장은 장 상태만 바꾸지 않고 모든 답과 학번 칸을 '확인 필요'로 바꾼다. 판독과 양식
  인식은 같은 신뢰 판정(`PageAlignment.trusted`)을 쓴다. 독립 검토 뒤에 한 가지를 더했다.
  어느 영역이든 한 칸(행이나 열) 옮겼을 때 인쇄된 동그라미에 분명히 더 많이 맞으면(옮긴
  변의 칸 수 절반 이상, 최소 3개) 그 장을 믿지 않는다. 제자리에 맞는 영역은 모든 칸이 이미
  동그라미 위에 있어 옮겨서 얻을 것이 없으므로 이 검사는 맞는 장을 막지 않는다.
- **채점 이미지(3.7).** 문항 번호 칸의 빨간 × 대신 빨간 빗금을 긋는다. ×가 두 자리 문항
  번호를 가렸다. 상단의 점수·범례는 넣지 않았다. 점수는 앱 화면에 있고 머리글이 이름
  칸을 가릴 수 있다. 미응답과 중복은 주황이 아니라 오답과 같은 빨강으로 그린다. 둘 다
  0점으로 확정된 값이고, 주황은 아직 정해지지 않은 '확인 필요'에만 쓴다.
- **양식 범위(3.2).** 보기 5개 양식만 지원한다(4개는 다음 버전). 빈 양식 PDF 등록과 150 DPI
  미만 이미지 경고는 넣지 않았다. 문항 번호는 왼쪽 세로 띠부터 위에서 아래로 매긴다.
  위아래로 쌓인 블록을 가로 방향으로 번호 매긴 양식은 잘못 매겨지므로 확인 창의 범위와
  미리보기로 확인해야 한다.
- **측정 안정성.** 인쇄된 원의 반지름을 재는 샘플링은 OpenCV 지도 크기 한도(32,767행)를
  넘지 않도록 나눠서 한다. 큰 해상도의 예전 프로필에서 모든 장이 오류로 끝나던 문제를
  독립 검토에서 찾았다. OpenCV 오류는 그 장의 오류로 보고된다.
- **양식 재사용(3.2).** 저장된 양식은 구조가 같고, 확인한 장마다 신뢰 판정을 통과하고
  동그라미 75% 이상이 맞으며, 맞춤 오차 중앙값이 그 장들로 새로 만든 양식의 1.3배 + 0.03
  이하일 때만 다시 쓴다. v3에서 손으로 그린 Tmot_OMR100은 0.15~0.20, 새로 만든 양식은
  0.05~0.07이라 다시 쓰지 않는다(그 양식으로 읽으면 파트1의 2장이 통째로 검토로 갔다).
  처음에는 고정 기준 0.1을 썼지만, 0.5mm 급지 흔들림이 있는 장에서는 새로 만든 양식도
  0.13~0.14가 되어 같은 양식을 매번 새로 묻게 되므로 상대 기준으로 바꿨다(독립 검토).
  새로 만든 양식도 확인한 장의 3분의 2 이상에서 신뢰 판정을 통과해야 확인 창에 내놓는다.
  손으로 그린 양식이 자동으로 골라지던 문제는 어드바이저 점검에서 찾았다.
- **정답표 대조(3.2).** 경고 대신, 정답표에 양식에 없는 문항이 있으면 채점을 멈추고 문항
  번호를 알린다. 답안지 한 장이라도 그 문항이 없으면 멈춘다(다른 장에 손으로 입력한 값이
  막음을 풀지 않도록). 양식에 있지만 정답표에 없는 문항은 v3처럼 채점하지 않는다. 양식과
  정답표의 문항 수가 다르다는 경고는 넣지 않았다. 100문항 카드로 30문항 시험을 보는 일이
  흔해 매번 뜨게 되고, 그러면 사용자가 경고를 무시하게 된다. 머리글 줄 문제는 위의 줄 빼기로
  원인을 고쳤다.
- **학번(3.6).** 명단 대조는 v3 동작을 그대로 쓴다.
- **세션 고정(4).** 세션은 v3처럼 양식의 SHA-256, 판독 결과와 칸 위치를 저장한다. 재채점은
  저장된 판독 결과를 쓰므로 양식 파일이 없어도 된다. 양식 사본은 따로 두지 않는다.
- **작업 분담(6).** 대화 중에 만든 프로젝트 에이전트 정의는 같은 세션에서 불러와지지 않아
  기본 에이전트에 모델을 지정해 썼다(조사 Haiku, 화면 통합·테스트 Sonnet, 독립 검토 Opus).
