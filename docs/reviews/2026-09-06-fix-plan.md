## 2. 유지할 제품 계약

- Windows onedir 포터블: `OMR Grader.exe + _internal/` 폴더 전체를 이동 단위로 유지한다.
- 데이터는 EXE 옆 `Data/`, `Profiles/`, `config.json`, `logs/`에 둔다.
- 원본 스캔·정답표·검수 이미지의 대용량 파일 단일 저장 원칙을 유지한다.
- 학생·답안의 내부 연결 기준은 `work_item_id`이며 학번 중복을 덮어쓰기 근거로 쓰지 않는다.
- 소수 배점, 복수 정답의 집합 일치, 모두 정답, 미출제, 동점 등수 등 이미 확인한
  채점 규칙은 유지한다.
- 제거한 학번 수정·통합성적표 UI는 복원하지 않는다.
- 이전 시험 기록을 열기만 했을 때 내부 파일을 고쳐 쓰지 않는다. 변경은 정상적인
  저장 작업에서 새 generation을 원자적으로 게시하는 방식으로만 반영한다.

## 4. 단계별 수정 설계

### 0단계 — 기준점과 회귀 검사의 준비

1. 현재 HEAD·작업 트리와 기존 3개 검토 문서를 보존한다. 수정 작업은 별도 브랜치에서 수행한다.
2. 검토용 일회성 스크립트의 절대 경로를 제거하고 pytest 임시 폴더 fixture로 옮긴다.
3. 핵심 fixture를 Git에 보존한다. PNG·Excel·프로필은 합성 데이터로 실행 시 생성한다.
4. 기존 fixed20 형식의 스캔·채점 완료 세션, 수정 이력이 있는 구 형식, 손상된 형식의
   대조군을 확보한다. 실제 학생 자료 대신 합성 세션 사본을 사용한다.
5. 기존 테스트 2건의 경로 기대값과 제거된 API 수집 오류는 현재 제품 계약에 맞춰
   정리하되, 각 변경이 왜 필요한지 커밋에 기록한다.

기준 수치는 이전 검토의 1,023 통과 / 2 실패 / 14 skip / 수집 오류 1건과 별도 성능
하네스 36 통과다. 동일한 통과 개수를 목표로 삼지 않고, 유효한 검사의 보존과 신규 결함
회귀 검사를 기준으로 삼는다.

### 1단계 — R01: 보정 가능한 확정 응답과 이력을 보존

**설계 결정:** 수동 수정이 사라진 원시 `AutomaticPage` 전체의 재생성에 의존하지 않도록,
검증된 확정 응답을 보정의 기준 상태로 취급한다. 기존 `projection_request.json`을
가짜로 만들어 넣는 대신 보정 상태를 명시적으로 표현한다.

새 generation에 추가할 작은 구조화 자료 `correction_state.json`의 역할:

- 자체 형식 버전과 보정 기준이 된 snapshot/revision 식별 정보.
- 원래 `source_kind`, `work_item_id`, 학번 상태, 답안 `choices/status`를 보존한
  기준 `EffectiveResponse` 목록.
- 기준 이후 적용한 수정의 식별자·revision·before/after와 보존 가능한 이력 범위.
- 기준과 수정 이력을 적용한 결과가 `semantic_inputs.json`의 현재 응답·점수와
  동일한지 검증할 수 있는 정보.

새 자료는 manifest에 등록하고 lease로 읽는다. 해시를 자기 파일 안에 다시 포함시키는
순환 구조를 만들지 않는다. 이미지·PDF 복사본을 보정 상태 안에 넣지 않는다.

기존 자료 읽기 규칙:

| 저장 형식 | 처리 |
| --- | --- |
| 새 보정 상태가 있는 세션 | schema·snapshot·이력·현재 응답 일치를 검증하여 사용 |
| 기존 projection과 수정 이벤트가 유효하게 있는 세션 | 기존 의미를 검증하고 보정 기준 형태로 읽음; 알려진 이력 보존 |
| fixed20처럼 projection이 manifest에 없고 확정 응답·점수·필요 좌표가 유효한 세션 | 현재 revision을 명시적인 구 버전 보정 기준으로 읽음; 과거 상세 이력이 없다는 사실 보존 |
| manifest에 선언된 파일이 사라졌거나 hash/schema가 손상된 세션 | 오류 처리. 구 버전 호환 경로로 우회하지 않음 |

추가 수정:

- 채점·재채점·최종 확정·메타데이터 갱신 후에도 보정 상태와 알려진 이력을 이어서 보존한다.
- 수정 미리보기와 저장은 같은 lease/revision 및 원래 before 값을 기준으로 검증한다.
- 기존 이벤트 식별자와 중복 저장 방지 규칙을 유지한다. 사라진 과거 수정 이력을
  추정하여 만들어 넣지 않는다.
- `review_geometry.json`의 좌표와 현재 확정 응답을 상세 화면에 연결한다. 보정 셀 클릭,
  키보드 선택, 이미지 축소 후 좌표, 점수와 표시 결과까지 일치시킨다.
- 현재 UI의 단일 숫자/None 표시 때문에 다중 답·불확실 답을 빈 답으로 취급하지 않도록,
  보정 요청의 before 값에는 완전한 `AnswerValue`를 유지한다. 새로운 학번 수정 UI는 추가하지 않는다.
- 새 저장 실패 시 이전 CURRENT와 원본을 보존한다. 열기만 하는 호환 처리는 읽기 전용이다.

주요 파일:


필수 검사: 이미지 인식 → 채점 → 다중/불확실 답 수정 → 저장 → 재열기 → 다른 정답표로
재채점 → 백업 → 다른 폴더 복구 → 재수정. 새 세션과 fixed20 형식 모두 수행한다.
이 과정에서 스캔·검수 이미지가 중복 증가하지 않는지와 손상 자료 거부도 확인한다.

### 2단계 — R04·R06: 권한과 정답표 바이트의 일관성

**Windows 권한:** `os.access()`만으로 Windows 쓰기 권한을 판정하지 않는다.
현재 사용자 토큰과 파일·디렉터리의 보안 설명자를 사용하는 읽기 전용 권한 조회를
추가한다. 조회 실패는 쓰기 가능으로 추정하지 않고 제한 상태로 처리한다.

- 포터블 루트의 원자적 생성·교체 권한과 실제 관리 경로의 쓰기 요구를 확인한다.
- 기존 config/Data/Profiles가 있는 경우와 없는 경우를 모두 검사한다.
- 시작 시 및 실제 작업 중 권한 거부가 발생하면 controller의 변경 가능 상태와
  관련 버튼을 함께 전환하고 정확한 읽기 전용 안내를 표시한다.
- 권한 거부, 다른 프로세스의 잠금, 손상된 파일을 서로 다른 오류로 유지한다.
- 프로그램 시작 시 사용자 폴더에 probe 파일을 만드는 방식으로 기존의 쓰기 없는
  권한 조회 계약을 바꾸지 않는다. 실제 파일 생성 probe는 격리된 테스트에서만 사용한다.

주요 파일: `infrastructure/paths.py`, `capabilities.py`, 권한 조회용 새 내부 adapter,
`bootstrap.py`, `ui/app_controller.py`, `resources/messages.py`, 관련 설정·저장 경계.

**정답표 원본:** 한 번 읽어 고정한 바이트를 파싱·hash 계산·원본 보존에 함께 사용한다.
`workbooks/answer_key.py`에 바이트 기반 파서 경계를 만들고 기존 경로 기반 함수는
호환 wrapper로 유지한다. `AnswerKeyValidation`에서도 snapshot hash와 보존 바이트
hash 일치를 확인한다.

주요 파일: `workbooks/answer_key.py`, `application/answer_key_use_case.py`,
`application/dto.py`.

필수 검사: 실제 ACL 쓰기 거부·실행 중 권한 변경·변경 버튼 비활성화·파일 내용 무변경,
읽기 시점 사이의 정답표 변경·잠금·깨진 Excel·보존 원본과 사용 정답의 동일 hash.

### 3단계 — R02·R07: 재현 가능한 개발 환경과 안전한 빌드

- 빌드에 필요한 `packaging/OMR_Grader.spec`, 공식 도구, 유효한 테스트와 지원 코드를
  명시적으로 Git 추적 대상으로 만든다.
- 테스트별 의존 관계를 정리한다. 과거 onefile 경로에 매달린 배포 테스트는 현재
  onedir 계약을 검증하도록 대체한다. 삭제된 제품 기능을 시험하는 경우에는 근거를
  남겨 정리한다. 단순한 실패 은폐용 skip은 추가하지 않는다.
- `pyproject.toml`에 `dev` / `build` 의존성 그룹을 제공하고 Windows Python 3.12용
  잠금 목록을 관리한다. 기존의 미추적·해시 없는 옛 lock을 검증된 lock으로 부르지 않는다.
- `.gitignore`에는 사용자 `Data/`, `Profiles/`, `config.json`, 로그·잠금과 검토 산출물의
  제외 규칙을 명확히 유지한다. 테스트 데이터는 합성 생성 코드로 보존한다.
- 개발·빌드 지원 기준은 **Windows x64 + Python 3.12 + PowerShell 7.2 이상**으로
  명시한다. PowerShell 5.1에서는 버전 요구사항을 먼저 안내하며 OS 실행 정책을 자동 변경하지 않는다.

WorkRoot 정책은 **기존 폴더를 지우는 입력이 아니라 새 작업 폴더를 만들 부모 경로**로 정한다.
기본값은 저장소의 `build/`다. 그 아래 시도별 고유 하위 폴더를 생성하고 반환한다.

- Python·PyInstaller·spec·출력 경로를 먼저 확인한다.
- 최종 절대 경로·링크 여부·허용 범위·출력 충돌을 확인하고 빌드 경로를 예약한다.
- 정리는 이번 실행이 생성한 고유 하위 폴더에만 적용한다. 사용자 지정 부모 폴더와
  기존 파일, 기존 fixed 산출물은 삭제하거나 덮어쓰지 않는다.
- 실패한 시도는 실패 기록을 남기고 최종 배포 경로로 게시하지 않는다.

주요 파일: `.gitignore`, `pyproject.toml`, `requirements/`, `packaging/OMR_Grader.spec`,
`tools/build-portable-folder.ps1`, `tests/`, `README.md`.

필수 검사: 완전히 새 체크아웃에서 문서 명령만으로 설치·테스트·빌드,
spec/Python 누락 시 기존 sentinel 보존, 동시 빌드 출력 충돌 거부, 기존 fixed20 보존.

### 4단계 — R03·R05: 배포 내용과 실행 결과를 실제로 검증

PowerShell wrapper의 인터페이스는 유지하되, 엄격한 JSON/경로/ZIP 검증은 테스트하기
쉬운 Python 모듈 `tools/portable_release.py`로 정리한다. writer와 verifier가 공유하는
코드가 있더라도 테스트의 예상 hash·내용은 별도의 통제 fixture에서 생성한다.

새 receipt 형식은 version 2로 명시하고 다음을 묶는다.

- 제품 버전, 실제 Git HEAD와 빌드 입력 목록·hash.
- spec·공식 빌드/검증 스크립트·의존성 lock·사용 도구 버전.
- EXE 및 전체 배포 파일의 상대 경로·크기·SHA-256.
- ZIP은 self-hash 순환이 없도록 외부 hash/검증 보고서로 바인딩한다.

검증 조건:

1. JSON의 중복 키, 잘못된 schema·hash, 선언 누락을 거부한다.
2. 절대 경로·`..`·Windows 드라이브/ADS·예약 이름·대소문자 충돌·링크 및 중복
   항목을 거부한다. 파일 읽기 전에 payload 내부 경로임을 확인한다.
3. 디스크의 실제 파일 목록을 receipt와 완전히 대조한다. 미등록 DLL도 거부한다.
4. ZIP 각 파일의 실제 바이트·크기·CRC·hash와 receipt를 비교한다. 내부 receipt는
   외부 receipt와 동일해야 하며 sidecar도 필수 확인한다.
5. 실제 빌드 입력의 hash를 빌드 전후 비교한다. 입력이 중간에 달라지면 승인 가능한
   산출물로 게시하지 않는다. 최종 후보 빌드는 확정된 깨끗한 커밋에서 수행한다.
6. fixed20의 구 receipt는 제한된 이력 검사로 식별하고, 새 기준으로 검증하지 못한
   출처 정보는 미확정으로 표시한다. 옛 receipt를 새 형식처럼 고쳐 쓰지 않는다.

smoke 조건:

- ZIP 검증이 끝난 해제 사본을 실행한다. 디스크 폴더만 실행하여 ZIP 검증을 대신하지 않는다.
- 제목만 같은 스플래시를 성공으로 인식하지 않는다. 메인 창의 식별 정보와
  초기화 완료·작업 가능 상태를 확인한 뒤 종료/조작한다.
- writable 검사는 실제 설정 저장 또는 합성 세션 저장 후 재열기를 확인한다.
- read-only 검사는 시작 성공, 읽기 전용 안내, 변경 버튼 비활성화와 전체 파일 내용
  무변경을 확인한다. PermissionError, 비정상 종료, 관찰 실패를 PASS로 처리하지 않는다.
- main PID뿐 아니라 해당 실행이 만든 하위 프로세스를 추적·정리한다. ACL과
  프로세스 정리 실패도 보고한다. 준비 전 닫기, 준비 후 닫기, 작업 취소 후 닫기를 구분한다.
- 기본/`-StrictShutdown` 옵션 구분은 유지하고 각 검사 상태·실행 범위를 출력한다.
  `-Smoke None` 성공을 전체 실행 검증 완료로 표현하지 않는다.
- **이번 2.1.1 후보의 최종 검증은 `-Smoke Both -StrictShutdown`을 사용한다.**
  종료 실패를 해결하지 못하면 원인을 보고하고 승인 가능한 최종 후보 판정은 보류한다.

주요 파일: `tools/portable_release.py`(신규), `tools/build-portable-folder.ps1`,
`tools/verify-portable-folder.ps1`, `tools/smoke-portable-onedir.py`,
필요한 시작 상태 관측 경계, `tests/packaged/`, `tests/integration/test_portable_relocation.py`.

필수 검사: 검토의 모든 변형 fixture가 올바른 사유로 거부됨. 정상 대조군·실행·저장은
성공하고, 손상·실행 실패·권한 거부 사례가 잘못된 PASS가 되지 않음.

### 5단계 — R08: 화면의 가용 크기에 맞는 창과 조작 영역

- `screen.availableGeometry()`를 기준으로 초기 창 크기를 제한한다.
- 고정된 `1280×800` 최소값을 낮추는 것에 그치지 않고, 작은 창에서도 주 작업 버튼과
  학생 표·답안 검토 영역에 접근할 수 있게 scroll/splitter와 레이아웃을 조정한다.
- 기존 테마와 시각적 정체성을 유지하고 불필요한 재디자인은 하지 않는다.
- 화면 이동/배율 변경 후 선택 학생·미저장 수정·키보드 포커스를 보존한다.

주요 파일: `ui/main_window.py`, `ui/detail_page.py`, `ui/scan_page.py`,
`ui/grading_page.py`, 필요한 `ui/theme.py` 규칙과 GUI 테스트.

검사 행렬: 1366×768/100%, 1920×1080/100·125·150·200%의 가용 논리 크기,
라이트·다크, 키보드만으로 주요 조작. 논리 resize 검사와 실제 화면 조작의 증거를 구분한다.
실제 OS 배율/별도 계정 확인이 불가능한 항목은 임의로 PASS 표시하지 않는다.

### 6단계 — 의존성·문서·버전 정리

- Qt 보안 공지와 현재 Windows wheel 제공을 확인한 **PySide6 6.11.2**를 우선 적용
  대상으로 고정한다. Essentials/Addons/Shiboken도 동일 버전으로 맞춘다.
- 업무 로직 수정과 의존성 변경을 별도 커밋으로 분리하여 회귀 원인을 구분한다.
- PyInstaller와 hook은 우선 검토 환경의 6.14.1 / hooks-contrib 2026.6을 출발점으로
  새 Qt와의 빌드·번들 검사를 수행한다. 호환성 문제가 있으면 근거를 남겨 필요한
  최소 변경을 정하고, 문제가 남은 상태로 구버전을 조용히 배포하지 않는다.
- PyMuPDF·Qt 등 번들 제3자 라이선스/고지 자료를 포함하고 적용 내역을 문서화한다.
  프로젝트 자체 라이선스 변경이나 상용 계약 구매는 이 승인 범위에 포함하지 않는다.
- `pyproject.toml`, `src/omr_grader/__init__.py`, README, AGENTS의 버전을 `2.1.1`로
  맞추고 `docs/releases/2.1.1.md`에 수정 범위·호환성·제한을 기록한다.
- 실제 설치/빌드 명령, PowerShell 요구사항, onedir 이동 방법, 구 세션 읽기와 새 저장,
  검사별 PASS의 의미 및 최종 검증 명령을 문서에 반영한다.

확인한 외부 근거:

- [Qt SVG 보안 공지](https://www.qt.io/blog/security-advisory-type-confusion-and-heap-buffer-overflow-vulnerability-in-qt-svg-marker-handling): 해당 문제의 수정 기준을 6.11.1 이상으로 안내.
- [PySide6 6.11.2](https://pypi.org/project/PySide6/6.11.2/): 2026-08-18 공개, Windows x64 wheel과 Python 3.12에 맞는 ABI 제공을 확인.

이 확인은 후보 의존성을 정한 근거이며 앱 호환성 검사 완료를 뜻하지 않는다.

### 7단계 — 확정 커밋에서 최종 후보 빌드

1. 모든 소스·테스트·문서 변경을 확정하고 로컬 커밋한다.
2. 해당 커밋의 새 체크아웃·새 가상환경에서 설치 및 전체 유효 테스트를 수행한다.
3. 그 입력으로 onedir를 빌드하고 receipt·ZIP·검증 보고서를 생성한다.
4. 검증된 ZIP 해제본에서 대표 업무 흐름과 strict smoke를 수행한다.
5. 최종 HEAD·입력 hash·EXE/ZIP hash·테스트/종료/호환성 결과를 묶어 보고한다.

현재 다음 fixed 번호는 21이지만, 실제 빌드할 때 기존 산출물 목록에서 번호를 정한다.
진단용 작업은 별도 scratch에서 수행하여 매번 배포본을 늘리지 않는다.
기존 fixed20과 그 ZIP/receipt는 보존한다.

## 6. 데이터 보존과 되돌리기

- 개발·호환성 검사는 별도 임시 폴더의 합성 세션 및 복사본에서 수행한다.
- 사용자 실제 포터블 루트로 검증 범위를 확장해야 할 경우, 프로그램 종료와 전체 백업을
  먼저 확인하고 별도 방향을 받는다. 이번 승인만으로 원본 세션을 일괄 변경하지 않는다.
- 구 버전 호환 읽기가 실패하면 해당 세션은 읽기/복구 가능한 상태를 보존하고,
  원본 JSON을 직접 덮어써서 맞추지 않는다.
- 수정판으로 저장한 세션에 구 EXE를 다시 덮어쓰는 방식의 롤백을 권하지 않는다.
  롤백은 수정판 사용 전의 포터블 폴더/백업 사본으로 한다.
- 포터블 경로 변경, 채점 규칙 변경, 대량 데이터 변환 등 이 계획 밖의 변경이 필요하면
  근거와 영향을 정리해 다시 승인받는다.

## 8. 하위 모델 구현과 독립 검토

사용자의 추가 요청에 따라 실제 코드·테스트 수정은 하위 모델이 담당한다.
주 에이전트는 작업 명세와 파일 소유 범위 지정, 변경 검토, 검증 실행, 통합 결과 확인 및
사용자 보고를 담당한다. 구현 결함을 발견하면 담당 하위 모델에 수정 요청을 돌려보낸다.
주 에이전트가 기능 코드를 대신 작성하여 완료 처리하지 않는다.

| 작업 묶음 | 담당 모델 | 소유 범위와 순서 |
| --- | --- | --- |
| 핵심 기능 A | `gpt-5.6-terra`, `high` | R01·R04·R06의 domain/application/infrastructure, 관련 bootstrap/UI 연결 및 해당 회귀 테스트 |
| 빌드·검증 B | `gpt-5.6-terra`, `high` | R02·R03·R05·R07의 tools/packaging/개발 의존성/추적 규칙 및 배포 테스트 |
| 화면·의존성 C | `gpt-5.6-terra`, `high` | A·B 검토·통합 후 R08과 Qt 업데이트. A·B가 수정한 파일은 완료 확인 후 소유권을 넘겨받음 |
| 안전성 독립 검토 S | `gpt-5.6-sol`, `high` | 통합 후보의 기존 세션 호환·보정 이력·데이터 보존 및 ZIP/receipt/권한 검증의 누락·우회·거짓 PASS를 독립 점검. 코드 수정은 하지 않음 |

| 검토·최종 판정 | 현재 주 에이전트 | diff 검토, 기존 세션 호환성·오류 주입·실제 EXE 검사, 재수정 요청, 통합 및 완료 판정 |

동시에 실행하는 하위 에이전트는 S를 포함해 최대 2개로 제한한다. A와 B가 같은 파일을 동시에
수정하지 않도록 세부 테스트 파일까지 소유 범위를 지정한다. B의 smoke에 제품 시작
상태 변경이 필요하면 A에 요청하여 반영한다. 공통 fixture·설정 파일도 한 담당자만 수정한다.

각 하위 모델의 제출물은 변경 파일, 실제 diff/커밋, 실행한 테스트와 원시 결과,
남은 실패·미확정 사항이다. 완료했다는 요약만으로 통합하지 않는다.

S는 구현된 통합 후보가 준비된 뒤 한 번 검토하고, 지적 사항 수정 후 같은 에이전트에서
해당 항목을 재확인한다. 검토 범위는 R01의 구 세션 읽기·원자 저장·이력 보존과
R03–R05의 무결성·권한·실행 판정 경계에 집중한다. 코드·테스트·판정 기준은 수정하지
않으며, 필요한 검사는 지정된 임시 폴더에서 수행한다. 심각도, 파일·줄, 재현 절차와
근거, 수정 권고를 주 에이전트에게 제출한다. 실제 수정은 A/B/C 담당에게 돌려보내고,
최종 완료 판정은 주 에이전트가 직접 검증한 결과로 내린다.

주 에이전트의 검토 순서:

1. 승인된 파일 범위와 데이터 보존 계약 준수 확인.
2. 실제 구현에서 실패를 숨기는 fallback, 테스트 삭제, 판정 완화가 없는지 확인.
3. 기존 재현 사례와 새 회귀 검사를 독립 실행.
4. 부족한 부분은 파일·줄·재현 결과를 지정하여 구현 담당에게 재수정 요청.
5. 통합된 커밋에서 새 체크아웃과 실제 EXE의 최종 검사 수행.

모델 설정은 상속에 맡기지 않고 역할별 모델과 추론 설정을 명시한다. 사용자의 최신
지시에 따라 **모든 하위 모델의 추론 상한은 high**다. Terra 구현 담당과 Sol 검토 S는
`high`, Luna 문서 담당은 `medium`을 사용한다. `xhigh`, `max`, `ultra` 및 고속 설정은
사용하지 않으며 자동 승격하지 않는다. 이 상한은 앞선 xhigh/ultra 선택 지침보다 우선한다.
기존 Sol 제외 방침은 **독립 검토 S 한 역할에만 예외**를 적용한다. Sol을 일반 구현에
사용하지 않는다. 지정 모델이나 설정이 호출 시 지원되지 않으면 실제 오류를 보고하고
허용되지 않은 모델이나 high 초과 설정으로 대체하지 않는다.

현재 세션의 호출 도구에서 Terra/Sol의 high와 Luna의 medium 선택지를 확인했다. 공식 문서도
하위 에이전트별 모델·추론 설정과 역할 분리를 설명한다.
